# 탐색/검색 알고리즘 의사결정 기록(ADR)

본 문서는 상세설계서 4.3 절의 간결한 대안입니다. 정량 표 대신, 의사결정의 맥락과 선택, 파급효과만 기록합니다.

---

## 1) 유저 탐색(단건 조회/권한 확인/오토컴플릿)

- Context
  - 사용자 단건 조회가 매우 빈번하고 지연에 민감함. 주로 `user_id`·`username` 등 식별자 기반 조회.
  - 앱 계층 캐시를 일부 활용하고, 영속 계층은 RDB를 사용함.

- Options
  - (A) 순차 탐색
  - (B) 정렬 리스트 + 이진 탐색
  - (C) 앱 캐시 해싱 + DB 기본 키 인덱스(B-Tree)
  - (D) 정렬 맵(레드-블랙 트리 계열)

- Decision
  - (C) 해싱을 앱 계층 기본 조회로 채택, 영속 계층은 PK/B-Tree 인덱스 사용
  - 이름 접두사 오토컴플릿은 초기엔 정렬 리스트+이진 탐색, 규모 확대 시 Trie/검색엔진으로 승격

- Rationale
  - 해싱은 평균 O(1)로 응답시간 최소화, 구현 단순, 캐시 친화적
  - DB의 PK 인덱스는 신뢰성과 일관된 성능 제공

- Consequences
  - 캐시 동기화·만료 전략 필요
  - 접두사 검색은 별도 자료구조/엔진으로 운용

---

## 2) 게시물 검색(키워드 검색/정렬/페이지네이션)

- Context
  - 제목/본문 키워드 검색과 최신/인기 정렬이 핵심 요구
  - 초기 릴리스는 단일 RDB로 운영, 운영 복잡도 최소화가 중요

- Options
  - (A) 순차 포함 검색
  - (B) LIKE + 일반 인덱스
  - (C) DB 내장 FTS(예: SQLite FTS5, PG tsvector, MySQL FULLTEXT)
  - (D) ElasticSearch 등 전용 검색엔진

- Decision
  - 초기엔 (C) 내장 FTS 채택(하이라이트/랭킹/형태소 옵션 활용)
  - 데이터/트래픽 확대 시 (D)로 승격(파이프라인/인프라 추가)

- Rationale
  - 내장 FTS는 구현/운영 복잡도 대비 검색 품질과 성능이 우수, 이식성 높음

- Consequences
  - FTS 튜닝 필요(토큰화, 랭킹, 스톱워드)
  - 승격 시 ETL/동기화/클러스터 운영 비용 증가

---

부록: 적용 지침
- 정렬/페이지네이션은 `created_at`, `like_count` B-Tree 인덱스로 지원
- Top-K(실시간 인기글)는 min-heap 또는 DB 정렬+LIMIT 조합
- 소규모 도메인 매핑(오행/간지)은 해시(dict)로 충분
