# 탐색/검색 알고리즘 Pros/Cons 비교 요약

표 형태로 간단 비교 후 최종 선택을 명시합니다.

## 1) 유저 탐색(단건/식별자 기반)

| 후보 | 장점 | 단점 |
|---|---|---|
| 순차 탐색 | 구현이 매우 단순 | O(n)로 지연 큼, 데이터 증가에 취약 |
| 정렬+이진 탐색 | O(log n) 조회, 오토컴플릿 범위 탐색에 유리 | 삽입 시 정렬 유지 비용, 동적 업데이트 부담 |
| 해싱(앱 캐시) | 평균 O(1) 조회, 코드 단순, 캐시 친화 | 해시 충돌/메모리 사용, 캐시 동기화 필요 |
| 정렬 맵(RB-Tree) | 정렬 집합 유지, 순위/범위 질의 용이 | 파이썬 표준 부재, 구현 복잡도 ↑ |

- 최종 선택: 앱 계층은 해싱, DB는 PK/B-Tree 인덱스. 오토컴플릿은 소규모에 이진 탐색, 확대 시 Trie/검색엔진.

## 2) 게시물 검색(키워드/랭킹)

| 후보 | 장점 | 단점 |
|---|---|---|
| 순차 포함 검색 | 구현 매우 단순 | 성능 취약, 실사용 불가 수준 |
| LIKE+일반 인덱스 | 익숙한 SQL, 간단 | 어휘/형태소 처리 미흡, 대량 데이터 한계 |
| DB 내장 FTS | 구현/운영 단순, 랭킹/하이라이트 지원 | 튜닝 필요(토큰화/스톱워드), DBMS 종속성 |
| ElasticSearch | 고성능/확장성, 풍부한 쿼리 | 초기 학습/인프라/운영 비용 큼 |

- 최종 선택: 초기엔 DB 내장 FTS, 트래픽 확대 시 ElasticSearch로 승격. 정렬/페이지네이션은 인덱스(`created_at`, `like_count`) 사용.
